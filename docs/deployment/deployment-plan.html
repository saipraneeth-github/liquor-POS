1. Overview & Scope

1.1 Purpose of the release

Take a tested build of <APP_NAME> — a point-of-sale, inventory and accounting platform for liquor retail stores and bars in India (single stores or multi-store syndicates) — from source control to live hosting, with a database change path, verification and a tested way back. Optional release items: the database index/constraint package in docs/db-optimization/ (separately gated, §4.7).

1.2 System components

API + web serverNode.js ≥ 22, Fastify 5 (@fastify/jwt, helmet, cors, rate-limit, multipart). One process serves /api/v1/*, /health and the built React app at / (any unknown path falls through to the SPA). Listens on 0.0.0.0:$PORT (default 3001).

3. Build Process

3.1 Branching, tagging and versioning

  • Trunk-based: short-lived feature branches → PR → main (protected: required review + green CI). Commit style: conventional commits (feat(scope):, fix:, chore(db):).
  • Release: cut release/x.y from main; only fixes land there. Tag vX.Y.Z on the release commit (annotated, signed if possible).
  • Versioning: SemVer. MAJOR = breaking API/contract or non-additive schema change; MINOR = backward-compatible feature (including additive migrations); PATCH = fix. The image tag is the git tag plus the short SHA: <REGISTRY>/<APP_NAME>:1.4.0 and :1.4.0-a1b2c3d. Never deploy latest. Align package.json version (currently 0.1.0) with the tag.

4. Database Setup & Migration

4.1 Provisioning (first install only)

# as DBA, on the DIRECT endpoint
createdb -h <DB_HOST> -U <DB_ADMIN> <DB_NAME>
psql "<DB_ADMIN_URL>" -c "CREATE ROLE <APP_DB_USER> LOGIN PASSWORD '<from vault>';"
psql "<DB_ADMIN_URL>" -c "GRANT CONNECT ON DATABASE <DB_NAME> TO <APP_DB_USER>;"
# app user owns the objects it migrates (Drizzle creates tables, enums, indexes)
psql "<DB_ADMIN_URL>" -c "ALTER DATABASE <DB_NAME> OWNER TO <APP_DB_USER>;"

Enable point-in-time recovery and note its window. Use the pooled URL in DATABASE_URL for the running app and the direct URL for migrations and backups.

4.2 Migration scripts and execution order

Migrations are the ordered SQL files drizzle/0000_… → 0024_… listed in drizzle/meta/_journal.json; Drizzle applies the ones not yet recorded in drizzle.__drizzle_migrations, in journal order, inside one transaction — a failure rolls the whole pending batch back (which is also why CREATE INDEX CONCURRENTLY cannot go through it). Order of operations for every release: migrate first, then deploy the app — a missing column fails every bill because the counter-sheet handler runs inside the bill transaction.

Compatibility rule: release N's schema must work with release N-1's code (add columns/indexes/tables; never drop or rename in the same release — use expand → migrate → contract over two releases). This is what makes an application-only rollback safe (§11).

4.3 Running the migration

# release job (has devDependencies + the repo at the release tag), DIRECT url, from a bastion/CI runner
git checkout v<RELEASE_VERSION>
npm ci
export DATABASE_URL="<DB_ADMIN_URL>"          # direct, not -pooler
npm run db:migrate                            # prints "Migrations applied"

# confirm
psql "$DATABASE_URL" -tc "select count(*) from drizzle.__drizzle_migrations;"   # expect 25 + new ones

4.4 Backup before migration (mandatory gate)

# 1) provider snapshot / branch + note the timestamp (preferred, instant)
# 2) logical dump as a second copy, stored outside the DB account, encrypted
pg_dump -Fc -h <DB_HOST> -U <DB_ADMIN> -d <DB_NAME> -f pre_<RELEASE_VERSION>_$(date +%F_%H%M).dump
pg_restore --list pre_<RELEASE_VERSION>_*.dump | head      # proves the file is readable
sha256sum pre_<RELEASE_VERSION>_*.dump > pre_<RELEASE_VERSION>.sha256

Restore rehearsal: restore the dump to staging at least once per quarter and before any first release.

4.5 Seed data

  • Do not run npm run db:seed in production. It creates demo users with a known password and refuses to run when NODE_ENV=production unless ALLOW_PROD_SEED=1 — leave that unset.
  • Create the first Super Admin (the software provider's platform owner) on the server against the production URL: npm run super-admin (see src/db/create-super-admin.ts); store the generated credentials in the vault and force a password change.
  • Reference data (categories, GST rates, sale types) is loaded by the onboarding workflow / agreed import — <REFERENCE_DATA_SOURCE>.

4.6 Validation after migration (read-only SQL)

-- run the package from docs/db-optimization/sql/tests/
psql "$DATABASE_URL" -f t02_business_invariants.sql   -- every violations = 0
psql "$DATABASE_URL" -f t03_referential_integrity.sql -- must return no rows
psql "$DATABASE_URL" -f t01_fingerprint.sql > fp_after.txt   -- compare with fp_before.txt for DDL-only releases

4.6a Rollback scripts

Drizzle migrations have no automatic down step. Rollback options, in order of preference: (1) leave the additive schema in place and roll back only the application; (2) run the release's hand-written *_down.sql (the docs/db-optimization phases ship tested ones); (3) restore the §4.4 backup / PITR. Every migration PR must state which of the three applies.

4.7 Optional release item — index & constraint package

docs/db-optimization/ contains Phase 1 (41 indexes, built CONCURRENTLY, no data change) and Phase 2 (11 CHECKs + 2 foreign keys, NOT VALID then validated, pre-check required). Deploy it as its own change after the application release is stable; follow its 08-deployment-runbook.md. Run the _concurrent files with psql on the direct connection — they cannot go through the migrator or a transaction pooler.

5.4 Scaling and statefulness

  • CPU-bound work: password hashing (bcrypt) on login and invoice OCR. Start at 2 replicas × 1 vCPU / 1 GiB; horizontal autoscaler on CPU 65 % (min 2, max <MAX_REPLICAS>). Uploads are limited by MAX_UPLOAD_BYTES (invoice.routes.ts); allow that body size at the load balancer.
  • No sticky sessions needed (JWT bearer tokens).
  • Per-instance state (G6): login throttle and rate limits are in memory — limits multiply by replica count. The billing/dunning timer (every 6 h) also runs inside every process unless BILLING_JOB_ENABLED=0. Reminders are guarded by a unique index (uq_dunning_once), so duplicates are prevented, but run it on one instance (set =0 on the rest) to avoid wasted work and racing invoice generation.
  • DB connections: pooled endpoint; keep replicas × pool size below the pooler's limit. Each cash bill makes ≈ 24 queries, so app and database must be in the same region (§10.3).

5.5 Networking, load balancer and TLS

  • Load balancer (L7): terminate TLS, HTTP→HTTPS 301, health check GET /health (expect 200), idle timeout ≥ 60 s, request body limit ≥ MAX_UPLOAD_BYTES, forward X-Forwarded-For/Proto and set TRUST_PROXY to the hop count.
  • Certificates: managed certificate (ACM / Let's Encrypt) for <APP_DOMAIN>, auto-renew, alert 21 days before expiry. TLS 1.2+ only; HSTS (max-age ≥ 31536000) at the edge — verify the header in §10.
  • The app server is not publicly addressable: only the load balancer may reach port 3001.

7.1 Controls

AreaControl (and what the code already does)
SecretsFrom <VAULT> at deploy time; image contains none; CI uses short-lived tokens; secret scanning on every push. The app refuses to start with a missing/short JWT_SECRET, a wildcard CORS_ORIGIN, or the test payment gateway in production.

11. Rollback Plan

11.1 Triggers (any one)

  • Smoke test 3–7 or 12 fails and is not fixable in 20 minutes.
  • 5xx rate > 2 % for 5 minutes, or bill-create p95 > 2× baseline, or no bills can be created.
  • Data-integrity check (t02/t03) reports a violation after the release.
  • Security finding rated High/Critical introduced by the release.

Decision-maker: RM with the Engineering Lead. Time-box: decide within 15 minutes of the first trigger; prefer rolling back to fixing forward during trading hours.

11.2 Application rollback (default path, ~10 min)

kubectl rollout undo deploy/<APP_NAME>                    # or redeploy the previous immutable tag
kubectl rollout status deploy/<APP_NAME>
# restore the previous env set from the vault if it changed; re-run smoke tests 1–5

Safe because the schema is additive and backward-compatible with release N-1 (§4.2). Do not run the migrator in reverse.

11.3 Database rollback (only if the schema/data change itself is the fault)

#Step
1Stop writes: scale the app to 0 (or enable maintenance mode at the LB) and tell outlets to use the offline queue.
2Prefer the release's tested *_down.sql (e.g. docs/db-optimization/sql/002_integrity_down.sql, then 001_indexes_down_concurrent.sql) — no data impact.
3If data was corrupted: restore to the pre-release snapshot/PITR timestamp into a new database, validate with t01–t03, then repoint DATABASE_URL. Writes made after the restore point are lost — export bills/vouchers created since the snapshot first (created_at > <SNAPSHOT_TIME>) and re-key or replay them under finance supervision.
4Deploy the previous image against the restored database; run the smoke suite; re-open traffic.
5Record exactly what was lost/replayed in the incident ticket.
