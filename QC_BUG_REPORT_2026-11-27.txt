QC-001 — HIGH — Missing non-default sale-type price falls back to Walk-in MRP

Area:
  Billing, sale-type stock allocation, Counter Stock Sheet

Business rule violated:
  A non-default sale type is its own price list. No product_prices row means
  the item is not sold under that type and billing/stock transfer must return
  422 until a price is set.

Reproduction:
  1. Choose a product with a normal MRP but no Janata price.
  2. Attempt a Janata bill for that product.
  3. The server does not report the missing Janata price. It resolves the
     Walk-in/MRP price and proceeds to the stock check instead.
  4. Attempt to move that product into the Janata counter.
  5. The transfer is accepted (201) although no Janata price exists.

Observed evidence:
  tests/integration/sale-types.int.test.ts:83 expected "No Janata price" but
  received "Insufficient stock".
  tests/integration/sale-types.int.test.ts:145 expected an unpriced Janata
  transfer to return 422 but received 201.
  The remaining nine sale-type failures cascade because the first stateful
  setup test stops before its intended transfers and sales.

Root cause:
  src/modules/catalog/price.engine.ts:54
  For a non-default type, resolveUnitPrice() currently returns:
    branch type price ?? tenant type price ?? base Walk-in/MRP price
  The final "?? base" makes an unpriced non-default type saleable.

Expected:
  For a non-default type, return only its branch-specific type price or its
  tenant type price. Return null when both are absent. Billing and transfer
  must then reject the operation with a clear missing-price error.

Impact:
  - Janata or another counter can sell at the wrong legal/commercial price.
  - Stock can be allocated into a counter that should not sell that product.
  - Counter-sheet revenue and accounting can be calculated using the wrong rate.
  - This is a core money and inventory rule, so release is blocked.

Suggested regression gate:
  Fix resolveUnitPrice(), then require all 14 tests in
  tests/integration/sale-types.int.test.ts to pass from a fresh database.

QC-002 — MEDIUM — Day Closing payment fields have no accessible names

Area:
  Day Closing

Affected controls:
  frontend/src/closing/Closing.tsx:595  #closingUpiSales
  frontend/src/closing/Closing.tsx:635  #closingCardSales
  frontend/src/closing/Closing.tsx:678  #closingCreditSales

Reproduction:
  1. Open Day Closing as manager/office admin/owner.
  2. Inspect the accessibility tree or navigate the three amount inputs with
     a screen reader.
  3. The fields have visible nearby headings, but no <label for>, wrapping
     <label>, aria-label or aria-labelledby association.

Observed:
  The responsive DOM audit reported all three unnamed inputs at phone, tablet
  and desktop sizes. Manual source inspection confirmed the missing association.

Expected:
  Each financial input announces its purpose, for example "UPI sales amount",
  "Card sales amount" and "Khata / customer credit sales amount".

Impact:
  Screen-reader and voice-control users cannot reliably identify which amount
  they are editing. A wrong entry affects end-of-day reconciliation.

Suggested fix:
  Associate the existing visible text with each input using <label htmlFor>,
  or add a unique accessible name with aria-labelledby.
